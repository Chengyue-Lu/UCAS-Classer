# v1.1.x -> v1.3.0 路线

更新时间：2026-03-31

## 当前判断

`1.1.1` 之后，项目已经进入“主线可用、边界清楚、靠真实使用反馈继续收口”的阶段。  
因此 `1.1.x` 更适合做维护修复，`1.2.0` 更适合作为一版“稳定性 + 体验 + 发布流程”收口，`1.3.0` 再承接一个真正新的产品增量方向。

## 1.1.x 维护重点

### 1. 作业详情作为主线

- 继续清洗详情正文，压掉课程平台里杂乱的 HTML 与空结构
- 处理图片、附件、复杂正文的可读性
- 保证作业列表状态、详情状态、详情 URL 三者一致
- 继续验证缓存命中与重抓时机，让详情链表现更稳定

### 2. 登录态与运行时稳定性

- 继续观察 `check -> interrupt -> recovery` 这条链
- 优先区分“cookie 失效”和“临时离线 / 校园网切换 / DNS 异常”
- 保持“失败不急于删除旧登录态”的原则
- 继续复核后台 cookie refresh 的真实效果和触发时机

### 3. 提醒与采集可信度

- 继续验证 `summary -> full` 升级是否足够敏感且不过度
- 继续观察通知 / 资料 / 作业提醒是否有重复、漏报或误报
- 如果后续加日志，也应优先加在调度和提醒边界，而不是 UI 表面

### 4. 打包与安装体验

- 继续保证主仓与 package 的同步边界清楚
- 保持 fresh install 的默认路径、资源准备、版本号更新流程稳定
- 每次修 runtime 都要顺手复核 package 行为，不把 package 当“自动跟上”

## 1.2.0 建议目标

### 1. auth / runtime 韧性更强

- 让 interrupt 恢复逻辑对真实网络波动更温和
- 减少“需要人工重新登录，但其实只是临时断网”的误判
- 让手动 `check`、后台 `check`、cookie refresh 的职责更清楚

### 2. 作业详情体验更完整

- 在 `1.1.x` 已打通的基础上，把详情展示真正做顺
- 处理图片、附件、多段正文、长内容阅读体验
- 让“列表摘要 -> 详情打开 -> 本地缓存”这条链更可解释

### 3. 应用自动检测更新

- 先做轻量版更新检测，不急着做静默更新
- 支持启动时检查新版本
- 支持设置页手动检查更新
- 检测到新版本后提示并跳转下载页

### 4. 发布与维护流程更顺

- 文档、同步、打包、版本号更新的流程再压平一轮
- 让“主仓修复 -> package 同步 -> 打包验证”更像固定流水线
- 把阶段文档及时归档，避免交接入口再次变旧

## 1.3.0 重要功能方向

### 1. 课表整合进主程序

- 把课表作为正式模块组合进现有课程体系
- 让用户能在同一应用里看到课程列表、课表视图和课程相关内容
- 课表数据源和更新策略应尽量复用现有采集与本地存储能力

### 2. 以课表为中心组织待办

- 围绕课表时间轴整合作业、提醒、个人待办
- 让“课程 -> 时间 -> 待办事项”形成更自然的组织方式
- 优先做和课程强相关的待办，不急着扩成泛用效率工具

### 3. 日常使用入口更统一

- 让 dashboard、课程详情、课表、提醒之间的跳转更顺
- 把用户高频动作尽量收敛到少数几个稳定入口
- 避免课表功能成为孤立新页面，而是作为主线信息组织升级

## 暂不建议在 1.2.0 / 1.3.0 做重投入的方向

- 作业代提交
- 大范围 UI 重做
- 再起一轮架构级重构
- 与核心“课程 / 课表 / 资料 / 通知 / 作业 / 提醒”无关的外围功能扩张

## 一个简化判断

如果只用一句话概括：  
`1.1.x` 负责把作业详情和稳定性做扎实，`1.2.0` 负责把更新与维护链条做顺，`1.3.0` 再把课表和待办整合成真正的新主线。
